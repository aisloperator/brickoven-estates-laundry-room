# CLAUDE.md

Guidance for working in this repo.

## What this is

`index.html` is an interactive 3D preview of the Brickoven Estates laundry room, rendered with Three.js. It is a single self-contained file with no build tooling required to *view* it — Three.js and OrbitControls are inlined so it runs fully offline in Chrome, Firefox, and Safari (drag/scroll/pinch to orbit, zoom, pan).

`index.html` is generated. Do not hand-edit it — edit the source below and run `./build.sh`.

## Source layout

- `src/app.js` — all scene logic: room/wall/appliance geometry, materials, procedural canvas textures, lighting, camera, and OrbitControls setup. This is the file to edit for new features.
- `src/shell-head.html` — everything before the big inline `<script>`: doctype, `<head>`, styles, and the body's static DOM (`#c` canvas, `#title`, `#hint`, `#fallback` overlays).
- `src/shell-tail.html` — closes the `<script>` tag and the document.
- `vendor/three.min.js`, `vendor/OrbitControls.js` — Three.js r0.128.0 (global/UMD build) and its matching non-module `OrbitControls.js`, vendored verbatim so the page needs zero network access. Don't bump the version casually — newer Three.js releases dropped the non-module `examples/js/controls/OrbitControls.js` in favor of ES modules, which would break the "single inlined script" approach this page relies on.
- `build.sh` — concatenates `shell-head.html` + `<script>` + the two vendor files + `app.js` + `shell-tail.html` into `index.html`. Run it after any change under `src/` or `vendor/`. It's deterministic — same inputs always produce byte-identical output.

## Scene conventions (in `src/app.js`)

- Units are meters. Room is `ROOM_W` (X) × `ROOM_D` (Z), walls are `WALL_H` tall / `WALL_T` thick.
- The back wall (at Z≈0, spanning X) holds the washers; it's split by a doorway gap (`doorGapStart`/`doorGapEnd`) with trim casing. The right wall (at X≈ROOM_W, spanning Z) holds the dryers, at a right angle to the back wall. There is no ceiling and only these two walls exist — it's an open-corner diorama so the orbit camera can always see inside.
- `makePoster(width, height, texture)` builds a framed sign (dark frame box + a `PlaneGeometry` face using the given texture) in the same local convention as the appliances — front at local +Z — so it mounts on a wall the same way they do. It doesn't build its own texture; `createPosterTexture(bgColor, borderColor, lines, extra)` is the generic content generator (`lines` is `{text, y, color, font}[]`, empty for blank; the optional `extra(ctx)` callback runs after the text for any non-text drawing a design needs — currently only `donationPosterTexture` uses it, to draw a heart via `drawHeart(ctx, cx, cy, size, color)`), and each distinct design gets its own thin wrapper that calls it — `dryerWarningPosterTexture()`, `promptRemovalPosterTexture()`, `heDetergentPosterTexture()`, `donationPosterTexture()` — so adding a new poster design is a new wrapper function, not a new fork of the canvas-drawing code. (There's no `blankPosterTexture` anymore — it was removed once nothing referenced it; a one-line `createPosterTexture(bg, border, [])` brings it back if a placeholder is needed again.) There are 4 posters: one over dryer 6 on the right wall (`dryerWarningPosterTexture`, `rotation.y = -Math.PI / 2` since that wall faces -X, positioned at `ROOM_W - 0.02`, roughly `dryerCenters[0]`), and 3 more on the back wall above the washers (no rotation needed — the back wall already faces +Z, matching a poster's own local convention directly — at `z = 0.02`, just proud of the wall), textures `[heDetergentPosterTexture, promptRemovalPosterTexture, donationPosterTexture]` left-to-right (index 0 is genuinely leftmost in world X here — unlike the dryer wall, there's no facing-direction ambiguity on the back wall — so the array order matches reading order left to right). The 3 back-wall posters are evenly distributed by dividing the span from washer 1's left edge to washer 5's right edge into 3 equal segments and centering one poster in each (`washersLeftEdge + washersSpan * (pi + 0.5) / 3`), and vertically centered between the tallest washer's top and the wall top (`(Math.max(flH, tlH) + WALL_H) / 2`). None of the posters are in `machines` — not clickable, purely decorative.
- `createBookPile(count, numCols, maxRadius)` builds a messy pile/stack of hardcover-book boxes (90 total, split across 4 stacks — see below). Each book gets a 6-material array (`BoxGeometry`'s per-face order is `[+X,-X,+Y,-Y,+Z,-Z]`; the book lies flat with width on X, thickness on Y, depth on Z) so the spine (-X) and front/back covers (+Y/-Y) get a random solid color (`coverMat`, fresh per book) while the fore-edge (+X) and top/bottom edges (+Z/-Z) get the shared cream `bookPageMat` — that's what makes it read as a book rather than a flat-colored block. Books are assigned round-robin to `numCols` random small "columns" within `maxRadius` of the group origin (each column has its own running height `col.h`) rather than each getting an independent random position, so they visibly stack rather than floating individually; a small fraction get an extra tilt (`rotation.x`/`z`) for an occasional askew/half-toppled book.
- **Book placement — the front-left corner** (where x=0 meets z=ROOM_D): `cornerStackSpecs` places 4 stacks (tighter columns/radius than the default, `createBookPile(count, 3, 0.16)`) here — one tight in the corner itself, one along the x=0 edge, one along the z=ROOM_D edge (the room's far/open edge — geometrically the opposite side from the washer wall, even though neither has an actual wall mesh), and one further along that same far edge. Each stack sits `edgeInset` (0.2) from whichever edge(s) it's against — just enough clearance for its own radius, i.e. genuinely up against the edge rather than set back from it — and consecutive stacks are spaced 0.33 apart (0.825 for the fourth, further one), half their original separation. This corner has no wall geometry (the back wall is at z=0 with the washers, the right wall is at x=ROOM_W with the dryers — x=0 and z=ROOM_D are both open), but it's clear of every appliance's footprint regardless of x, since nothing extends anywhere near z=ROOM_D. (A brief detour moved the books to the back-right corner — the one with two real walls — reasoning that hiding them from the initial camera there would need less trickery. That wasn't the ask; reverted. The books belong in the front-left corner regardless of what the initial camera does or doesn't include.)
- Appliance factories (`makeFrontLoad`, `makeTopLoad`, `makeStackedDryerColumn`) build geometry in a **local convention**: footprint centered on X, back face at local Z=0, front face at local Z=depth, base at Y=0. Placing an appliance is then just `position.set(x, 0, z)` for wall-facing-+Z placements (the washers), or the same plus `rotation.y = -Math.PI / 2` to face -X (the dryers on the right wall) — that rotation maps local +Z to world -X and local +X to world +Z, which is why the dryer row is laid out along `dryerCenters` (a Z-axis layout) even though the factory itself only knows about local Z depth.
- `layoutRow(widths, start, end, gap)` centers a row of items with given widths/gap inside a `[start, end]` span. `layoutRowAnchored(widths, gap, anchorIndex, anchorCenter)` instead keys the whole row off one item's fixed center, laying the rest out from there — used when a specific machine's position must not move even as the gap/spacing changes. Both washer and dryer rows currently use the anchored version: `washerCenters` calls `layoutRow` once just to read off where the old evenly-centered layout put washer 5 (the last one), then feeds that as the anchor to `layoutRowAnchored` with the real (1-inch) gap — so washer 5 stays put regardless of gap changes to the other 4. `dryerCenters` does the same anchored on dryer 6 (the standalone unit, index 0). Add/resize appliances by editing the `widths` arrays and factory calls, not by hand-placing coordinates — and if you add a machine or change which one should stay fixed, update the anchor index/lookup, not just the gap.
- Textures (brick walls, floor tile, control-panel decal) are generated procedurally on `<canvas>` at load time — no image assets. If you add a new canvas texture, set `tex.encoding = THREE.sRGBEncoding` on it (the renderer is configured for sRGB output; color-map textures left at the default `LinearEncoding` render washed out). The control-panel decal is *not* shared — `createLogoTexture(label, showCommercial, mainFontSize)` is called fresh per machine (via `decalPlane(w, h, label, showCommercial, mainFontSize)`) since each one's label text (its identifying number) differs; don't reintroduce a single module-level `logoTex` instance. `showCommercial`/`mainFontSize` are only `true`/`46` for front-load washers (`makeFrontLoad` computes `isFrontLoadWasher = doorStyle !== 'rect'` — dryers use the same factory with `doorStyle: 'rect'`, so that one check distinguishes them); everything else (dryers, and `makeTopLoad`'s washers, which always pass `false, 58`) gets a bigger label with no "COMMERCIAL" subtitle, vertically re-centered in the decal since there's no second line under it.

## Click-to-play dog animation

Clicking (or tapping) any washer/dryer plays a scripted animation, built as an ordered list of steps in `startDogShow(machineRoot)`: walk in through the doorway → approach and face the machine → open its door/lid → pull the laundry up into its mouth → shake it for 1s → carry it to a random spot near the middle of the floor → spit it out → lift a leg and pee on it for 2s (bright yellow stream, with a puddle on the floor that grows to match) → back up a step, still facing it → breathe red/orange fire at it for 1s → the laundry catches and burns with its own flame for 1s, charring from its original colors to black as it shrinks to nothing, with the puddle rushing away (ease-out shrink, gone well before the laundry finishes burning) → door closes itself → walk back out. This is the "more features coming soon" part of the codebase — expect it to keep growing.

- **Machine registry**: `makeFrontLoad`/`makeTopLoad` mark their returned group with `userData.isMachineRoot = true` plus `userData.kind` (`'front'`/`'top'`), `doorPivot`/`lidPivot`, `doorOpenAngle`, `userData.machineNumber`/`userData.machineLabel` (see below), and two invisible `Object3D` markers — `doorOpening` (where laundry emerges) and `standMarker` (where the dog stops, one appliance-depth in front of the door). Every individually-clickable unit (5 washers + 5 dryers, including each stacked-dryer half) is pushed into the flat `machines` array as it's placed; that array is what gets raycast.
- **Machine numbers**: every machine has a stable identifying number in `userData.machineNumber` (int) and `userData.machineLabel` (its on-panel text, e.g. `"WASHER 2"`/`"DRYER 7"`) — these are load-bearing for future features, not just display, so don't renumber casually. Assigned where each machine is placed (search `washerNumber`/`'DRYER '` in the placement code), not inside the factories themselves (which don't know their own position): washers 1-5 left to right along `washerCenters` (`wi + 1`); dryer 6 is the standalone unit nearest the doorway; the 2x2 stacked array is 7-10, assigned per column as `topNumber = 5 + idx * 2`, `bottomNumber = topNumber + 1` for `idx` 1 then 2 (i.e. 7/8 = top/bottom of the first stacked column, 9/10 = top/bottom of the second). The "leftmost"/column-order wording in the numbering request maps to the order machines are encountered walking along the back wall then around onto the dryer wall (increasing x, then increasing z) — *not* literal screen-left/right when facing the dryer wall head-on, which would invert it (dryers face -X, so smaller z is actually stage-right from that vantage). If that turns out to be the wrong reading, this is the place to fix it — `machineNumber`/`machineLabel` are threaded through `makeFrontLoad`/`makeTopLoad`/`makeStackedDryerColumn` and the decal, so renumbering is just changing the values passed at the placement call sites.
- **Hinges, not static doors**: front-load doors are a child `doorPivot` group hinged on the door's left edge (`rotation.y` swings it open); top-load lids are a child `lidPivot` group hinged on the back edge (`rotation.x` tilts it open). A dark disc/tub mesh sits behind/under each, revealed once the door or lid opens.
- **Top-load lid hinge is placed relative to the console, not the cabinet edge**: `makeTopLoad` computes `consoleY`/`consoleZ`/`consoleFrontZ` first (pushed close to the cabinet's back edge — `consoleZ = depth * 0.07` — to leave as much depth as possible for the lid in front of it), then derives `hingeZ = consoleFrontZ + lidH + 0.01` — just in front of the console by the lid's own thickness — and sets `lidPivot`'s z to that instead of the old `depth/2 - lidDepth/2` (which hinged near the cabinet's back edge, right where the console already was). `doorOpenAngle` is exactly `-Math.PI / 2`: at precisely vertical, the rotation math collapses so the *entire* lid — regardless of position along its length — ends up at a single z position (`hingeZ - lidH` to `hingeZ`), independent of y, standing as a flat panel directly in front of the console rather than sweeping up and away from it. (Any angle short of exactly vertical reintroduces a y/z coupling where the parts of the lid at the console's z-depth end up well above the console's height range — that's the bug this hinge relocation fixes; tweaking the angle instead doesn't.)
- **Top-load lid is sized off width, not depth**: `lidDepth = lidW * 0.85` — approximately square — rather than a fraction of the cabinet's `depth` parameter, so it stays square-ish regardless of how deep the cabinet is. Because that made the lid deep enough to need real room to swing forward of the hinge, `tlD` (the top-load washer's own depth, set where `makeTopLoad` is called) was bumped from `0.68` to `0.8` — front-loaders and dryers are untouched, `layoutRow` only uses width for spacing so this doesn't affect the horizontal layout, only how far the top-loaders themselves protrude from the wall. The drum (`tub`) radius is `Math.min(lidDepth, lidW) * 0.46` — large, only slightly smaller than the lid's own footprint — and its position stays derived from `lidDepth`/`hingeZ` so it's still fully hidden under the closed lid.
- **The 2 front-load washers have an independently-taller control panel**: `makeFrontLoad`'s 6th param, `extraPanelH`, adds directly onto `panelH` (normally just `height * 0.16`) rather than being folded into the proportional formula — the washer call site passes `FOOT` (0.3048, ≈1ft) so the panel grows by that fixed amount on top of its usual proportional growth from the cabinet itself also being `FOOT` taller, while the dryers (which don't pass it) keep the plain proportional panel. Because a much taller panel would otherwise physically overlap the circular door above it, `doorY` is `Math.min(height * 0.42, panelBottom - 0.04 - doorR - 0.035)` — the normal proportional position, capped so the door is pushed down far enough to keep a 4cm gap below the panel. For every existing (non-washer) caller this cap doesn't bind and `doorY` is unchanged; check that inequality again if you make the panel taller still or shrink the cabinet.
- **Two front-load door looks**: `makeFrontLoad(width, height, depth, bodyMat, doorStyle)` takes an optional `doorStyle` — `'round'` (default: chrome-rimmed glass circle, used for the 2 front-load washers) or `'rect'` (white rounded-rectangle panel via `roundedRectShape` + `ExtrudeGeometry`, used for the standalone dryer and stacked dryers). Both hinge and swing open the same way; only the visible door mesh differs. The rect panel is sized with margin (`doorW`/`doorH` well past `doorR`) so it fully covers the circular drum hole behind it even with rounded corners cut in, and is extruded (`doorThickness`) rather than flat so it reads as a solid door and stays visible edge-on once swung open. The drum itself stays circular either way.
- **`roundedRectShape` is reused for the top-load lid too**: `makeTopLoad`'s lid is white (`applianceWhite`) and built the same way as the dryer door — a `roundedRectShape` extruded with `ExtrudeGeometry` — but since the lid's footprint is in the X/Z plane (not X/Y like a front-facing door) the resulting mesh gets `rotation.x = -Math.PI / 2` so the extrusion direction (the shape's local Z) becomes the lid's vertical thickness instead of its depth. Keep that rotation in mind if you ever resize or reposition the lid — the shape's two axes correspond to lid width and lid *depth*, not width and height.
- **Picking**: `pointerdown`/`pointerup` are compared by distance and elapsed time to distinguish a tap from an orbit-drag (OrbitControls listens to the same events independently) before raycasting against `machines`. A hit mesh's ancestor chain is walked up to the nearest `isMachineRoot` object.
- **Sequencer**: `Sequencer` is a minimal step player — an array of `{duration, update(t), onStart, onEnd}` objects played in order, driven from the main `animate()` loop via `sequencer.tick(now)`. `walkStep`/`turnStep` are the two reusable step builders (position/heading lerp plus a procedural leg-swing gait keyed off distance traveled, so a walk always ends on a neutral leg pose). Every position/heading is derived from the clicked machine's `doorOpening`/`standMarker` world positions and a freshly randomized floor spot, not hand-placed coordinates, so the same code works for any machine.
- **Doorway-to-washer pathing prefers a direct diagonal, but never through a washer**: the doorway sits on the *same* wall as the washers (unlike the dryer wall, which is perpendicular), so a straight `walkStep` between the doorway and a washer's `standMarker` can cut diagonally across the back wall's cabinet zone and clip through whichever washer sits between the two — most visibly when the target isn't the washer nearest the doorway. `washerFootprints` (built alongside the washers, one XZ bounding box per washer — depth varies by front-load vs top-load) plus `segmentIntersectsBox`/`pathClearOfWashers` (slab-method segment-vs-AABB test) let `planWalk(from, to, speed, excludeBox)` actually check whether the direct line is clear rather than assuming it isn't: if clear, it's one natural diagonal `walkStep`; if not, it falls back to `safeBackWallPath(from, to, speed)`, which routes via whichever endpoint's z is farther from the wall (a "strafing" leg beyond every cabinet's front face) then closes the remaining single-axis gap, dropping degenerate zero-length legs. `excludeBox` is the *target* washer's own footprint (looked up from `machineRoot.userData.machineNumber`) — walking up to its own `standMarker` obviously isn't a collision. `planWalk` is used for both the doorway→standMarker approach and the post-fire return trip (`backUpPos` can be on the far side of a washer from the doorway too); for dryer targets `excludeBox` is `null` and the direct path is always clear (dryers were already provably never at risk — different wall), so they're unaffected. Both branches return `{steps, finalHeading}` — callers need `finalHeading` (not a fixed formula) for whatever `turnStep`/heading comes next, since it depends on which path was taken.
- **Carrying the laundry**: while "in the dog's mouth," the laundry pile mesh is actually reparented as a child of `dog.neckPivot` at `dog.mouthLocalPos`, so it automatically follows every head shake and walk-cycle nod for free. It's reparented back to `scene` (at its current world position, via `getWorldPosition`) right before the spit-out toss. Any time a step needs a fresh world-space point mid-hierarchy-change, it calls `dog.root.updateMatrixWorld(true)` first — `three.js` only auto-refreshes matrices during `renderer.render()`, so a value read immediately after changing a rotation in the same frame needs an explicit refresh or it'll be one frame stale.
- **Fire**: two independent multi-cone helpers, no shared single-cluster builder anymore. `buildFlameTongues(scaleMul)` is the laundry's own burning-in-place fire — `count` (8) cones laid out around a small jittered ring (offset apart, all pointing straight up), so it reads as a licking fire instead of one cone shape; offsets are generated in a loop (angle + random ring radius) rather than a hand-placed array, so changing the count is one line. `buildFlameSpray(count, scaleMul)` is the dog's mouth-fire *breath* — visually similar goal, structurally different: all cones share one base point (the mouth) rather than being offset around a ring, and each is angled outward at a random angle (`theta` up to `maxSpread` off straight-ahead, random azimuth `phi`) via `quaternion.setFromUnitVectors(Vector3(0,1,0), dir)`, so it reads as flame spraying outward from a point instead of a tight beam or a single wide cone. Both are deliberately *not* additive blending — additive only adds light on top of whatever's behind it, so against this scene's bright background it washed out toward white instead of reading as orange/red — plus an explicit `renderOrder` per cone to keep layering stable across camera angles. Both store `userData.baseHeight`/`phase` per cone at creation so their step's `update(t)` can flicker each one's height independently (`Math.sin(t * 16 + phase)`); `buildFlameSpray` additionally stores `userData.dir` since re-deriving `position` each frame as `dir.multiplyScalar(h/2)` (rather than just `position.y`) is what keeps each cone's *base* anchored at the shared mouth point as its height changes — `ConeGeometry` is centered on its own origin, so scaling `scale.y` alone without that repositioning would slide the whole cone along its own axis instead of just changing its tip's reach.
- **Charring**: each `createLaundryPile` piece stores its randomly-picked color as `userData.origColor` at creation. The burn step's `update(t)` lerps `material.color` from that stored original toward the shared `charredColor` (near-black) using `t` directly, so it always interpolates from the *original* color rather than the previous frame's (which would drift/compound). Piece materials aren't shared across plays — a fresh `createLaundryPile()` runs every time — so there's nothing to reset between plays.
- **Cleanup**: the laundry pile, its burn-phase flame cluster, and the pee-stream mesh are created fresh per play and disposed (`geometry.dispose()`/`material.dispose()`) at the end of their step — the floor is left untouched, nothing persists between plays.

## Workflow

1. Edit `src/app.js` (or `src/shell-head.html` for DOM/CSS changes).
2. **Immediately before every commit** (not before building/testing — right before `git commit`, so the timestamp reflects the actual commit time as closely as possible): update the build timestamp in the `#title` link's `<span>` in `src/shell-head.html` — `AI Sloperator - ` followed by the current UTC time in ISO 8601 Zulu form (`date -u +"%Y-%m-%dT%H:%M:%SZ"`). This is the on-page version indicator; it must always reflect *this* commit, not a stale one from earlier in the session.
3. Run `./build.sh` to regenerate `index.html` (do this *after* the timestamp update in step 2, so the built file has the correct one).
4. Open `index.html` in a browser to check the change (no server needed).
5. Commit both the `src/`/`vendor/` changes and the regenerated `index.html` together.

The top-left title (`#title`) is a link to https://www.aisloperator.com/ — the whole block (both lines) is clickable, not just the top line. If you change the link target or the title text, keep `#title`'s CSS overrides for `:link`/`:visited`/`:hover`/`:active` (color/text-decoration) in `shell-head.html` — without them the browser's default link styling (blue, underlined, purple once visited) would show through.
