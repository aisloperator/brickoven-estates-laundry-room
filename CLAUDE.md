# CLAUDE.md

Guidance for working in this repo.

## What this is

`index.html` is an interactive 3D preview of the Brickoven Estates laundry room, rendered with Three.js. It is a single self-contained file with no build tooling required to *view* it — Three.js and OrbitControls are inlined so it runs fully offline in Chrome, Firefox, and Safari (drag/scroll/pinch to orbit, zoom, pan).

`index.html` is generated. Do not hand-edit it — edit the source below and run `./build.sh`.

## Source layout

- `src/app.js` — all scene logic: room/wall/appliance geometry, materials, procedural canvas textures, lighting, camera, and OrbitControls setup. This is the file to edit for new features.
- `src/shell-head.html` — everything before the big inline `<script>`: doctype, `<head>`, styles, and the body's static DOM (`#c` canvas, `#title`, `#randomFakeDataBtn`, `#hint`, `#fallback` overlays).
- `src/shell-tail.html` — closes the `<script>` tag and the document.
- `vendor/three.min.js`, `vendor/OrbitControls.js` — Three.js r0.128.0 (global/UMD build) and its matching non-module `OrbitControls.js`, vendored verbatim so the page needs zero network access. Don't bump the version casually — newer Three.js releases dropped the non-module `examples/js/controls/OrbitControls.js` in favor of ES modules, which would break the "single inlined script" approach this page relies on.
- `build.sh` — concatenates `shell-head.html` + `<script>` + the two vendor files + `app.js` + `shell-tail.html` into `index.html`. Run it after any change under `src/` or `vendor/`. It's deterministic — same inputs always produce byte-identical output.

## Scene conventions (in `src/app.js`)

- Units are meters. Room is `ROOM_W` (X) × `ROOM_D` (Z), walls are `WALL_H` tall / `WALL_T` thick.
- The back wall (at Z≈0, spanning X) holds the washers; it's split by a doorway gap (`doorGapStart`/`doorGapEnd`) with trim casing. The right wall (at X≈ROOM_W, spanning Z) holds the dryers, at a right angle to the back wall. There is no ceiling and only these two walls exist — it's an open-corner diorama so the orbit camera can always see inside.
- **Doorway trim overlaps its wall by design, but must not end flush with it**: each vertical `trimBox` post's outer edge sits 0.08 inside the adjoining wall segment (so it visually occludes the brick there), but its inner edge must stop *past* `doorGapStart`/`doorGapEnd`, not exactly on it — that boundary is precisely where the wall segment's own cut end-cap face already sits, and two coplanar faces (trim's white, the wall's brick) in the exact same spot z-fight (flickery/erratic rendering, worst right at the jamb, matching where a viewer is actually looking through the doorway). The posts are sized `0.086` wide instead of `0.08`, offset so the inner edge lands `0.006` past the gap boundary, into open air beyond the wall's edge — enough to break the tie without a visible step. The horizontal header trim above the doorway had the identical issue on its own axis: its bottom face used to land exactly at `y = doorHeight`, precisely where the brick header box's own bottom face already sits, so it's now `0.086` tall instead of `0.08`, positioned so its bottom lands `0.006` below `doorHeight` instead of exactly on it. If you resize the doorway or its trim, keep all three epsilons; snapping any of them back to exactly `doorGapStart`/`doorGapEnd`/`doorHeight` reintroduces the z-fight.
- `makePoster(width, height, texture)` builds a framed sign (dark frame box + a `PlaneGeometry` face using the given texture) in the same local convention as the appliances — front at local +Z — so it mounts on a wall the same way they do. It doesn't build its own texture; `createPosterTexture(bgColor, borderColor, lines, extra)` is the generic content generator (`lines` is `{text, y, color, font}[]`, empty for blank; the optional `extra(ctx)` callback runs after the text for any non-text drawing a design needs — currently only `donationPosterTexture` uses it, to draw a heart via `drawHeart(ctx, cx, cy, size, color)`), and each distinct design gets its own thin wrapper that calls it — `dryerWarningPosterTexture()`, `promptRemovalPosterTexture()`, `heDetergentPosterTexture()`, `donationPosterTexture()` — so adding a new poster design is a new wrapper function, not a new fork of the canvas-drawing code. (There's no `blankPosterTexture` anymore — it was removed once nothing referenced it; a one-line `createPosterTexture(bg, border, [])` brings it back if a placeholder is needed again.) There are 4 posters: one over dryer 6 on the right wall (`dryerWarningPosterTexture`, `rotation.y = -Math.PI / 2` since that wall faces -X, positioned at `ROOM_W - 0.02`, roughly `dryerCenters[0]`), and 3 more on the back wall above the washers (no rotation needed — the back wall already faces +Z, matching a poster's own local convention directly — at `z = 0.02`, just proud of the wall), textures `[heDetergentPosterTexture, promptRemovalPosterTexture, donationPosterTexture]` left-to-right (index 0 is genuinely leftmost in world X here — unlike the dryer wall, there's no facing-direction ambiguity on the back wall — so the array order matches reading order left to right). The 3 back-wall posters are evenly distributed by dividing the span from washer 1's left edge to washer 5's right edge into 3 equal segments and centering one poster in each (`washersLeftEdge + washersSpan * (pi + 0.5) / 3`), and vertically centered between the tallest washer's top and the wall top (`(Math.max(flH, tlH) + WALL_H) / 2`). None of the posters are in `machines` — not clickable, purely decorative.
- `createBookPile(count, numCols, maxRadius)` builds a messy pile/stack of hardcover-book boxes (90 total, split across 4 stacks — see below). Each book gets a 6-material array (`BoxGeometry`'s per-face order is `[+X,-X,+Y,-Y,+Z,-Z]`; the book lies flat with width on X, thickness on Y, depth on Z) so the spine (-X) and front/back covers (+Y/-Y) get a random solid color (`coverMat`, fresh per book) while the fore-edge (+X) and top/bottom edges (+Z/-Z) get the shared cream `bookPageMat` — that's what makes it read as a book rather than a flat-colored block. Books are assigned round-robin to `numCols` random small "columns" within `maxRadius` of the group origin (each column has its own running height `col.h`) rather than each getting an independent random position, so they visibly stack rather than floating individually; a small fraction get an extra tilt (`rotation.x`/`z`) for an occasional askew/half-toppled book.
- **Book placement — the front-left corner** (where x=0 meets z=ROOM_D): `cornerStackSpecs` places 4 stacks (tighter columns/radius than the default, `createBookPile(count, 3, 0.16)`) here — one tight in the corner itself, one along the x=0 edge, one along the z=ROOM_D edge (the room's far/open edge — geometrically the opposite side from the washer wall, even though neither has an actual wall mesh), and a fourth further along the x=0 edge — i.e. the third and fourth stacks flank the corner stack on *different* edges (one on each "arm" of the corner), not both continuing down the same one. Each stack sits `edgeInset` (0.2) from whichever edge(s) it's against — just enough clearance for its own radius, i.e. genuinely up against the edge rather than set back from it — and consecutive stacks along the same edge are spaced 0.33 apart, 0.25 for the further one — tightened twice from an initial looser layout, so don't read too much into the exact numbers beyond "close together." This corner has no wall geometry (the back wall is at z=0 with the washers, the right wall is at x=ROOM_W with the dryers — x=0 and z=ROOM_D are both open), but it's clear of every appliance's footprint regardless of x, since nothing extends anywhere near z=ROOM_D. (A brief detour moved the books to the back-right corner — the one with two real walls — reasoning that hiding them from the initial camera there would need less trickery. That wasn't the ask; reverted. The books belong in the front-left corner regardless of what the initial camera does or doesn't include.)
- Appliance factories (`makeFrontLoad`, `makeTopLoad`, `makeStackedDryerColumn`) build geometry in a **local convention**: footprint centered on X, back face at local Z=0, front face at local Z=depth, base at Y=0. Placing an appliance is then just `position.set(x, 0, z)` for wall-facing-+Z placements (the washers), or the same plus `rotation.y = -Math.PI / 2` to face -X (the dryers on the right wall) — that rotation maps local +Z to world -X and local +X to world +Z, which is why the dryer row is laid out along `dryerCenters` (a Z-axis layout) even though the factory itself only knows about local Z depth.
- `layoutRow(widths, start, end, gap)` centers a row of items with given widths/gap inside a `[start, end]` span. `layoutRowAnchored(widths, gap, anchorIndex, anchorCenter)` instead keys the whole row off one item's fixed center, laying the rest out from there — used when a specific machine's position must not move even as the gap/spacing changes. Both washer and dryer rows currently use the anchored version: `washerCenters` calls `layoutRow` once just to read off where the old evenly-centered layout put washer 5 (the last one), then feeds that as the anchor to `layoutRowAnchored` with the real (1-inch) gap — so washer 5 stays put regardless of gap changes to the other 4. `dryerCenters` does the same anchored on dryer 6 (the standalone unit, index 0). Add/resize appliances by editing the `widths` arrays and factory calls, not by hand-placing coordinates — and if you add a machine or change which one should stay fixed, update the anchor index/lookup, not just the gap.
- Textures (brick walls, floor tile, control-panel decal) are generated procedurally on `<canvas>` at load time — no image assets. If you add a new canvas texture, set `tex.encoding = THREE.sRGBEncoding` on it (the renderer is configured for sRGB output; color-map textures left at the default `LinearEncoding` render washed out). The control-panel decal is *not* shared — `createLogoTexture(label, showCommercial, mainFontSize)` is called fresh per machine (via `decalPlane(w, h, label, showCommercial, mainFontSize)`) since each one's label text (its identifying number) differs; don't reintroduce a single module-level `logoTex` instance. `showCommercial`/`mainFontSize` are only `true`/`46` for front-load washers (`makeFrontLoad` computes `isFrontLoadWasher = doorStyle !== 'rect'` — dryers use the same factory with `doorStyle: 'rect'`, so that one check distinguishes them); everything else (dryers, and `makeTopLoad`'s washers, which always pass `false, 58`) gets a bigger label with no "FRONT-LOADING" subtitle, vertically re-centered in the decal since there's no second line under it. `createLogoTexture`'s canvas is a fixed 512×128 (4:1) regardless of caller, so the `decalPlane(w, h, ...)` it's mapped onto has to keep roughly that aspect ratio or the text stretches; in `makeFrontLoad` the decal's height is `height * 0.16 * 0.7` — the plain proportional panel height, not the actual (possibly `extraPanelH`-inflated) `panelH` — specifically so the 2 taller-panel front-load washers don't get a squatter, more-square decal plane that stretches their text vertically relative to every other machine's.
- **Live machine status display**: `machineStatus` (in `src/app.js`, near `decalPlane`) is a plain object mapping machine number (1-10) to minutes left on its current run — `0` meaning idle/not running, and negative (currently only `-1`) meaning an error/unknown status — the shape a real status feed will eventually populate; every machine starts at `0` until then. `addStatusDisplay(g, machineNumber, x, y, z, w, h)` is called once per machine, inside `makeFrontLoad`/`makeTopLoad` right after that machine's decal, adding a floating `PlaneGeometry` with its own `CanvasTexture` (256×320, transparent background, `MeshBasicMaterial({transparent: true, side: THREE.DoubleSide})` so it's still legible if the camera orbits behind a machine) positioned in front of it, in the same local convention the factories already use (front face at local `Z = depth`), so it's placed once in local space and inherits whatever placement/rotation the machine itself gets, same as the decal. It returns the mesh so callers can set `castShadow = false` on it *after* their own `addShadowFlags(g)` call — `addShadowFlags` unconditionally turns `castShadow`/`receiveShadow` on for every mesh in the group, so disabling it has to happen after that call, not before, or it gets flipped back on; a floating hologram-style indicator has no business casting a shadow on the appliance or floor. `drawStatusCanvas(ctx, minutes)` draws a red X (`minutes < 0`), a bright green checkmark (`minutes === 0`), or the minutes as large bright red digits with smaller red "minutes" text underneath (`minutes > 0`) — plane width/height are derived from the appliance's own `width` (`width * 0.42 * 3 * 0.9` — the `* 3 * 0.9` chain preserves the original `0.42` sizing step and each later resize as its own factor, rather than collapsing them into one precomputed constant — height keeping the canvas's 320:256 aspect) so the text doesn't stretch, following the same lesson as the decal fix above. Centering differs by machine type, matching how each reads as "the machine" from the front: front-load washers and dryers (`makeFrontLoad`) center it on the door (`x=0, y=doorY`, matching the door's own center) rather than the panel; top-load washers (`makeTopLoad`) center it on the cabinet box (`x=0, y=tubY/2`) rather than the console/lid above it. Both use `z = depth + 0.4 * 0.25` (same chained-factor reasoning as the size), floating out in front of the machine. `makeFrontLoad` takes an optional trailing `statusY` param that overrides the door-centered height when given — used only at the 2 front-load washers' call site, passing `topLoadStatusY` (`tlH * 0.86 / 2`, mirroring `makeTopLoad`'s own `tubY / 2` formula) so the front-load washers' display sits at the same height as the top-load washers', instead of each washer type floating at its own unrelated height; the dryers (standalone and stacked) don't pass it and keep the plain `doorY` centering. Each display starts with `mesh.visible = false` — there's no data yet at construction time, so nothing should read as data before any exists — and only becomes visible the first time `setMachineMinutes` runs on it. `statusDisplays` holds each machine's `{ctx, tex, mesh}` so `setMachineMinutes(machineNumber, minutes)` can redraw the existing canvas, flag `tex.needsUpdate`, and reveal the mesh, all in place instead of rebuilding geometry. The **"Random Fake Data" button** (`#randomFakeDataBtn`, top-right, wired up near the render loop) calls `randomFakeData()`, which for each of the 10 machines first gives a 1/10 chance of `-1` (error/unknown status); otherwise a 0.5 chance of reading idle (`0`), and otherwise a random run length — washers (numbers 1-5) 1-35 minutes, dryers (6-10) 0-60 (dryers can independently land back on `0` from that branch too, on top of the shared 0.5 idle chance — that's intentional, not a bug, per how the randomization was specified). In the no-`?data=` (fake-data) path, `randomFakeData()` is also called once immediately at load, right after wiring the button's click listener — so the visualization is already populated on first render instead of showing nothing until a press; each subsequent press just re-randomizes on top of that. (The `?data=` path doesn't need an equivalent immediate call for the same reason — it already calls `resolveRealDataUrl(dataParam)` unconditionally at load, which populates the display once real data resolves.)
- **Render-on-demand**: `animate()` does *not* unconditionally call `renderer.render()` every `requestAnimationFrame` tick — the scene is static almost all the time (idle orbit, no dog-show/book animation running), so doing that would recompute the full frame (including a 2048×2048 `PCFSoftShadowMap` shadow pass) 60+ times a second for no visual change, burning CPU/GPU on an otherwise-idle tab. A `needsRender` flag (declared right after `controls`) starts `true` so the first frame still paints, and gets set again only when something that actually changes pixels happens: OrbitControls' own `'change'` event (covers both active dragging and its damping settling afterward — see the `EPS`-gated dispatch in `vendor/OrbitControls.js`, which stops firing once damping decays below its epsilon, so this doesn't degrade into a permanent per-frame flag), a window `resize`, an active dog-show/book-overlay sequencer step (`animate()` sets `needsRender = true` whenever either sequencer is running, ahead of ticking it), or `setMachineMinutes` redrawing a status display. `renderer.render()` only runs — and clears the flag — when `needsRender` is true. `renderer.shadowMap.autoUpdate` is set to `false` at renderer setup (its default is `true`) so the shadow pass doesn't get recomputed every tick either; `shadowMap.needsUpdate` is set right before each frame that does render, in the same `if (needsRender)` branch, so shadows still stay correct on every frame that actually draws. If you add new continuous per-frame scene mutation, it needs to set `needsRender = true` too, or it'll silently stop updating once the flag goes false.

## Click-to-play dog animation

Clicking (or tapping) any washer/dryer plays a scripted animation, built as an ordered list of steps in `startDogShow(machineRoot)`: walk in through the doorway → approach and face the machine → open its door/lid → pull the laundry up into its mouth → shake it for 1s → carry it to a random spot near the middle of the floor → spit it out → turn a quarter turn side-on to it → lift a leg and pee on it for 2s (bright yellow stream, with a puddle on the floor that grows to match) → turn back to face it → back up a step, still facing it → breathe red/orange/yellow fire at it for 1s → the laundry catches and burns with its own flame for 1s, charring from its original colors to black as it shrinks to nothing, with the puddle rushing away (ease-out shrink, gone well before the laundry finishes burning) → door closes itself → walk back out. This is the "more features coming soon" part of the codebase — expect it to keep growing.

- **Machine registry**: `makeFrontLoad`/`makeTopLoad` mark their returned group with `userData.isMachineRoot = true` plus `userData.kind` (`'front'`/`'top'`), `doorPivot`/`lidPivot`, `doorOpenAngle`, `userData.machineNumber`/`userData.machineLabel` (see below), and two invisible `Object3D` markers — `doorOpening` (where laundry emerges) and `standMarker` (where the dog stops, one appliance-depth in front of the door). Every individually-clickable unit (5 washers + 5 dryers, including each stacked-dryer half) is pushed into the flat `machines` array as it's placed; that array is what gets raycast.
- **Machine numbers**: every machine has a stable identifying number in `userData.machineNumber` (int) and `userData.machineLabel` (its on-panel text, e.g. `"WASHER 2"`/`"DRYER 7"`) — these are load-bearing for future features, not just display, so don't renumber casually. Assigned where each machine is placed (search `washerNumber`/`'DRYER '` in the placement code), not inside the factories themselves (which don't know their own position): washers 1-5 left to right along `washerCenters` (`wi + 1`); dryer 6 is the standalone unit nearest the doorway; the 2x2 stacked array is 7-10, assigned per column as `topNumber = 5 + idx * 2`, `bottomNumber = topNumber + 1` for `idx` 1 then 2 (i.e. 7/8 = top/bottom of the first stacked column, 9/10 = top/bottom of the second). The "leftmost"/column-order wording in the numbering request maps to the order machines are encountered walking along the back wall then around onto the dryer wall (increasing x, then increasing z) — *not* literal screen-left/right when facing the dryer wall head-on, which would invert it (dryers face -X, so smaller z is actually stage-right from that vantage). If that turns out to be the wrong reading, this is the place to fix it — `machineNumber`/`machineLabel` are threaded through `makeFrontLoad`/`makeTopLoad`/`makeStackedDryerColumn` and the decal, so renumbering is just changing the values passed at the placement call sites.
- **Hinges, not static doors**: front-load doors are a child `doorPivot` group hinged on the door's left edge (`rotation.y` swings it open); top-load lids are a child `lidPivot` group hinged on the back edge (`rotation.x` tilts it open). A dark disc/tub mesh sits behind/under each, revealed once the door or lid opens.
- **Top-load lid hinge is placed relative to the console, not the cabinet edge**: `makeTopLoad` computes `consoleY`/`consoleZ`/`consoleFrontZ` first (pushed close to the cabinet's back edge — `consoleZ = depth * 0.07` — to leave as much depth as possible for the lid in front of it), then derives `hingeZ = consoleFrontZ + lidH + 0.01` — just in front of the console by the lid's own thickness — and sets `lidPivot`'s z to that instead of the old `depth/2 - lidDepth/2` (which hinged near the cabinet's back edge, right where the console already was). `doorOpenAngle` is exactly `-Math.PI / 2`: at precisely vertical, the rotation math collapses so the *entire* lid — regardless of position along its length — ends up at a single z position (`hingeZ - lidH` to `hingeZ`), independent of y, standing as a flat panel directly in front of the console rather than sweeping up and away from it. (Any angle short of exactly vertical reintroduces a y/z coupling where the parts of the lid at the console's z-depth end up well above the console's height range — that's the bug this hinge relocation fixes; tweaking the angle instead doesn't.)
- **Top-load lid is sized off width, not depth**: `lidDepth = lidW * 0.85` — approximately square — rather than a fraction of the cabinet's `depth` parameter, so it stays square-ish regardless of how deep the cabinet is. Because that made the lid deep enough to need real room to swing forward of the hinge, `tlD` (the top-load washer's own depth, set where `makeTopLoad` is called) was bumped from `0.68` to `0.8` — front-loaders and dryers are untouched, `layoutRow` only uses width for spacing so this doesn't affect the horizontal layout, only how far the top-loaders themselves protrude from the wall. The drum (`tub`) radius is `Math.min(lidDepth, lidW) * 0.46` — large, only slightly smaller than the lid's own footprint — and its position stays derived from `lidDepth`/`hingeZ` so it's still fully hidden under the closed lid.
- **The 2 front-load washers have an independently-taller control panel**: `makeFrontLoad`'s 6th param, `extraPanelH`, adds directly onto `panelH` (normally just `height * 0.16`) rather than being folded into the proportional formula — the washer call site passes `FOOT` (0.3048, ≈1ft) so the panel grows by that fixed amount on top of its usual proportional growth from the cabinet itself also being `FOOT` taller, while the dryers (which don't pass it) keep the plain proportional panel. Because a much taller panel would otherwise physically overlap the circular door above it, `doorY` is `Math.min(height * 0.42, panelBottom - 0.04 - doorR - 0.035)` — the normal proportional position, capped so the door is pushed down far enough to keep a 4cm gap below the panel. For every existing (non-washer) caller this cap doesn't bind and `doorY` is unchanged; check that inequality again if you make the panel taller still or shrink the cabinet. The control-panel decal's own size is *not* derived from this inflated `panelH` — see the decal bullet below for why.
- **Two front-load door looks**: `makeFrontLoad(width, height, depth, bodyMat, doorStyle)` takes an optional `doorStyle` — `'round'` (default: chrome-rimmed glass circle, used for the 2 front-load washers) or `'rect'` (white rounded-rectangle panel via `roundedRectShape` + `ExtrudeGeometry`, used for the standalone dryer and stacked dryers). Both hinge and swing open the same way; only the visible door mesh differs. The rect panel is sized with margin (`doorW`/`doorH` well past `doorR`) so it fully covers the circular drum hole behind it even with rounded corners cut in, and is extruded (`doorThickness`) rather than flat so it reads as a solid door and stays visible edge-on once swung open. The drum itself stays circular either way.
- **`roundedRectShape` is reused for the top-load lid too**: `makeTopLoad`'s lid is white (`applianceWhite`) and built the same way as the dryer door — a `roundedRectShape` extruded with `ExtrudeGeometry` — but since the lid's footprint is in the X/Z plane (not X/Y like a front-facing door) the resulting mesh gets `rotation.x = -Math.PI / 2` so the extrusion direction (the shape's local Z) becomes the lid's vertical thickness instead of its depth. Keep that rotation in mind if you ever resize or reposition the lid — the shape's two axes correspond to lid width and lid *depth*, not width and height.
- **Picking**: `pointerdown`/`pointerup` are compared by distance and elapsed time to distinguish a tap from an orbit-drag (OrbitControls listens to the same events independently) before raycasting against `machines`. A hit mesh's ancestor chain is walked up to the nearest `isMachineRoot` object.
- **Sequencer**: `Sequencer` is a minimal step player — an array of `{duration, update(t), onStart, onEnd}` objects played in order, driven from the main `animate()` loop via `sequencer.tick(now)`. `walkStep`/`turnStep` are the two reusable step builders (position/heading lerp plus a procedural leg-swing gait keyed off distance traveled, so a walk always ends on a neutral leg pose). Every position/heading is derived from the clicked machine's `doorOpening`/`standMarker` world positions and a freshly randomized floor spot, not hand-placed coordinates, so the same code works for any machine.
- **Peeing side-on, not head-on**: the dog arrives at `randomSpot` already facing `carryHeading` (the direction it walked to get there), with the laundry (`laundryTarget`) sitting straight ahead of it along that same heading — so peeing without reorienting would mean facing the pile dead-on while lifting a hind leg toward it, which doesn't read as a real dog's stance. `peeHeading = carryHeading + Math.PI / 2` — a quarter turn — is enough on its own, with no repositioning: since the laundry is directly ahead pre-turn, rotating 90° swings the dog's local -X side (where `legBR`, the leg it lifts, lives — see `makeLeg(sx, sz)`, where `sx = -1` is the right/BR-FR side) to point at exactly the same spot the dog's front was just pointing at. A `turnStep(carryHeading, peeHeading, 300)` plays before the lift-and-pee step, and `turnStep(peeHeading, carryHeading, 300)` turns it back to face the laundry head-on afterward, before it backs up to breathe fire (which assumes `carryHeading`). The pee-stream geometry itself (`cylinderBetween(hipPos, laundryTarget, ...)`) doesn't care about orientation — it always connects `legBR`'s current world position to the target — so the turn is purely about making the *pose* read correctly, not about hitting the target.
- **Doorway-to-washer pathing prefers a direct diagonal, but never through a washer**: the doorway sits on the *same* wall as the washers (unlike the dryer wall, which is perpendicular), so a straight `walkStep` between the doorway and a washer's `standMarker` can cut diagonally across the back wall's cabinet zone and clip through whichever washer sits between the two — most visibly when the target isn't the washer nearest the doorway. `washerFootprints` (built alongside the washers, one XZ bounding box per washer — depth varies by front-load vs top-load) plus `segmentIntersectsBox`/`pathClearOfWashers` (slab-method segment-vs-AABB test) let `planWalk(from, to, speed, excludeBox)` actually check whether the direct line is clear rather than assuming it isn't: if clear, it's one natural diagonal `walkStep`; if not, it falls back to `safeBackWallPath(from, to, speed)`, which routes via whichever endpoint's z is farther from the wall (a "strafing" leg beyond every cabinet's front face) then closes the remaining single-axis gap, dropping degenerate zero-length legs. `excludeBox` is the *target* washer's own footprint (looked up from `machineRoot.userData.machineNumber`) — walking up to its own `standMarker` obviously isn't a collision. `planWalk` is used for both the doorway→standMarker approach and the post-fire return trip (`backUpPos` can be on the far side of a washer from the doorway too); for dryer targets `excludeBox` is `null` and the direct path is always clear (dryers were already provably never at risk — different wall), so they're unaffected. Both branches return `{steps, finalHeading}` — callers need `finalHeading` (not a fixed formula) for whatever `turnStep`/heading comes next, since it depends on which path was taken.
- **Carrying the laundry**: while "in the dog's mouth," the laundry pile mesh is actually reparented as a child of `dog.neckPivot` at `dog.mouthLocalPos`, so it automatically follows every head shake and walk-cycle nod for free. It's reparented back to `scene` (at its current world position, via `getWorldPosition`) right before the spit-out toss. Any time a step needs a fresh world-space point mid-hierarchy-change, it calls `dog.root.updateMatrixWorld(true)` first — `three.js` only auto-refreshes matrices during `renderer.render()`, so a value read immediately after changing a rotation in the same frame needs an explicit refresh or it'll be one frame stale.
- **Fire**: two independent multi-cone helpers, no shared single-cluster builder anymore. Both cycle each cone's color through the same 3-color palette (`colors[i % 3]`: `0xd22600` red, `0xff7a00` orange, `0xffd400` yellow) rather than a single fixed color, so the cluster reads as a mix of flame colors instead of a flat one. `buildFlameTongues(scaleMul)` is the laundry's own burning-in-place fire — `count` (10) cones laid out around a small jittered ring (offset apart, all pointing straight up), so it reads as a licking fire instead of one cone shape; offsets are generated in a loop (angle + random ring radius) rather than a hand-placed array, so changing the count is one line. `buildFlameSpray(count, scaleMul)` is the dog's mouth-fire *breath* — visually similar goal, structurally different: all cones share one base point (the mouth) rather than being offset around a ring, and each is angled outward at a random angle (`theta` up to `maxSpread` off straight-ahead, random azimuth `phi`) via `quaternion.setFromUnitVectors(Vector3(0,1,0), dir)`, so it reads as flame spraying outward from a point instead of a tight beam or a single wide cone. Both are deliberately *not* additive blending — additive only adds light on top of whatever's behind it, so against this scene's bright background it washed out toward white instead of reading as red/orange/yellow — plus an explicit `renderOrder` per cone to keep layering stable across camera angles. Both store `userData.baseHeight`/`phase` per cone at creation so their step's `update(t)` can flicker each one's height independently (`Math.sin(t * 16 + phase)`); `buildFlameSpray` additionally stores `userData.dir` since re-deriving `position` each frame as `dir.multiplyScalar(h/2)` (rather than just `position.y`) is what keeps each cone's *base* anchored at the shared mouth point as its height changes — `ConeGeometry` is centered on its own origin, so scaling `scale.y` alone without that repositioning would slide the whole cone along its own axis instead of just changing its tip's reach.
- **Charring**: each `createLaundryPile` piece stores its randomly-picked color as `userData.origColor` at creation. The burn step's `update(t)` lerps `material.color` from that stored original toward the shared `charredColor` (near-black) using `t` directly, so it always interpolates from the *original* color rather than the previous frame's (which would drift/compound). Piece materials aren't shared across plays — a fresh `createLaundryPile()` runs every time — so there's nothing to reset between plays.
- **Cleanup**: the laundry pile, its burn-phase flame cluster, and the pee-stream mesh are created fresh per play and disposed (`geometry.dispose()`/`material.dispose()`) at the end of their step — the floor is left untouched, nothing persists between plays.

## Click-to-read book overlay

Clicking any individual book in the corner piles (every book mesh is pushed into the flat `books` array as it's created, alongside — not merged with — `machines`) plays a short, independent animation: a dedicated book flies in small and distant while spinning, then swaps to an open two-page spread that unfolds to fill most of the screen with page text — the left page describes the bookshelves corner (books and videos, free to take or leave), the right page covers the countertop free-items spot next to it, the local curb-reuse tradition, and a note that clothing is best donated (not left out). Tapping anywhere while it's open dismisses it (pages swing shut, then it flies back down to nothing) — this doesn't require hitting the book again, and takes priority over every other click while showing.

- **One object, reused, not recreated per click**: unlike the dog show's laundry pile (randomized per play, so it's rebuilt fresh every time), the book overlay's content is fixed placeholder text — so `bookOverlay` and everything under it (`closedBook`, `pagesGroup`, both pages) are built once at scene-init time, and `openBook()`/`dismissBook()` just animate and toggle visibility on the existing objects.
- **Camera-attached, not world-attached**: `bookOverlay` is added via `camera.add(bookOverlay)`, and its position/rotation/scale are animated entirely in camera-local space — so it always reads as screen-filling regardless of where the orbit camera currently happens to be aimed, with no per-frame billboard math needed. This only works because `camera` itself is added to `scene` (`scene.add(camera)`, right where the camera is constructed) — `renderer.render(scene, camera)` only traverses what's reachable from `scene`, so a camera that isn't part of that graph would never have its children rendered even though its own view still works fine.
- **Sizing derived from fov/aspect, not a fixed number**: `openBook()` computes the visible height/width at a fixed depth in front of the camera (`bookFlyDepth`) from `camera.fov`/`camera.aspect` (the same trig as the initial camera-framing checks elsewhere in this file, just inverted — solving for visible size at a distance instead of checking whether a known point fits), then picks `finalScale` as whichever of width-fill or height-fill is more restrictive, so the open spread fills 78% of the screen without overflowing either dimension. Recomputed fresh on every `openBook()` call, so it stays correct across window resizes between plays.
- **Closed book vs. open pages are two separate objects, swapped, not one mesh doing double duty**: `closedBook` is a plain solid box, visible only during the fly-in; `pagesGroup` (a static spine box plus two hinged pages, hidden until the swap) becomes visible the instant `closedBook` is hidden, already sitting in its final flown-in position/scale. This is simpler than trying to morph one mesh between "thin flying box" and "flat open spread."
- **Page hinges follow the same door/lid hinge convention used for appliances**: each page is offset half a page-width away from its own pivot group's origin, so rotating the pivot (`leftPivot`/`rightPivot`) swings the whole page like a door. Closed = both pivots at 90°/-90° (pages folded edge-on against the spine, collapsing to a thin sliver); open = both at 0° (flat, coplanar, facing the camera directly — like a scanned book spread, not a slight V-tilt) — picked deliberately over a more "realistic" tilted-open book because it's simpler to get right and reads perfectly clearly as open.
- **Page textures reuse `createPosterTexture` directly**: no new texture generator was needed — a cream background/border with several centered `fillText` lines (manually broken to fit the canvas width, same as every poster's `lines` array) is exactly what a poster already does. The base page geometry is sized 1 : 512/384 to match that function's canvas dimensions 1:1, so the texture isn't stretched.
- **A blue cover plane rides behind each page, on the same pivot**: `leftCover`/`rightCover` are plain `bookCoverMat` (blue) planes, sized slightly larger than their page (`coverW`/`coverH` vs `pageW0`/`pageH0`) and positioned a hair behind it (`z = -0.01`, i.e. farther from the camera than the page, since the page's untransformed +Z normal already faces the camera — see the camera-attached note above), so it peeks out as a border instead of just being hidden directly behind. Each cover is a child of the *same* pivot as its page (not a separate hinge), so it opens and closes in lockstep with it for free. `closedBook` reuses the same `bookCoverMat`, so the flying closed book and the open covers are always the same color — change `bookCoverMat`'s color to recolor both at once.
- **Mutual exclusion with the dog show**: `bookBusy()` (true while flying/opening/showing) and `sequencer`/`bookSequencer`'s own done-flags gate both the machine-click and book-click paths in the shared `pointerup` handler, so a dog show can't start while a book is open or mid-animation and vice versa — same pattern as the dog show already used for itself, just extended to cover the second independent animation.

## Real machine status data (`?data=` query param)

This is the one place the page reaches out to the network at all — everything else is fully self-contained/offline, per the top of this file. If the page's own URL (the one it's loaded from, e.g. `index.html?data=<url>`) carries a `?data=<url>` param, `<url>` is treated as a **CSC Go** ("mycscgo.com") QR-code URL — the kind printed on a QR sticker on a real CSC Go washer/dryer, `https://mycscgo.com/qr/<code>`. This is the specific (and currently only) laundry-status provider this app knows how to talk to; an unrecognized `<url>` just leaves every machine unknown (see below), not an error.

- **CSC Go's site is a pure client-rendered SPA — there's no HTML or links to parse.** The raw page at a `mycscgo.com/qr/...` URL is just `<div id="root"></div>` plus two JS bundles; everything is rendered client-side after those load. Reverse-engineering the bundles (searching for GraphQL/REST operation names and route paths) turned up its `apollo-link-rest`-based API instead: plain, unauthenticated, CORS-open (`Access-Control-Allow-Origin: *`) REST `GET` endpoints under `https://mycscgo.com/api/v3/`. No cookies, tokens, or a headless browser are needed — confirmed directly with `curl` against a real QR code before writing any of this code.
- **Two-step resolution, matching the "find the actual data" ask**: `parseCscGoQrCode(url)` pulls the code out of the `/qr/<code>` path. `resolveRealDataUrl(dataParamUrl)` then does `GET .../api/v3/machine/qr/<code>`, which resolves that one QR code to its machine — including its `locationId`/`roomId`, which identify the whole room the machine sits in (this stands in for "the laundry summary link": there's no separate link to follow, but the same room-identification step). From there, `GET .../api/v3/location/<locationId>/room/<roomId>/machines` returns every machine in the room; that URL is what's stored in `realDataUrl` — "remembered" so later updates don't have to redo the QR resolution.
- **Field mapping is close to direct**: each object in the `.../machines` response has a `stickerNumber`, which matches this app's own 1-10 `machineNumber` convention (washers 1-5, dryers 6-10) directly, and a `timeRemaining` (minutes left, `0` when idle) that maps straight onto `machineStatus`'s existing values. `applyRealMachineList(list)` looks up each of the 10 `machineNumber`s by matching `stickerNumber`, and calls `setMachineMinutes` with `timeRemaining` — or `-1` if no machine with that `stickerNumber` came back, or its `timeRemaining` isn't a number. That's the same "data can't be loaded, show a red X" rule `-1` already existed for (see the status-display bullet above), reused here rather than inventing a separate error state.
- **Failure at either fetch step (network error, bad response, unrecognized `<url>`) falls back to `markAllMachinesUnknown()`** — every machine goes to `-1` — rather than leaving stale/fake data on screen or throwing.
- **Button swap, decided once at load**: `#randomFakeDataBtn` and `#updateRealDataBtn` (`src/shell-head.html`) occupy the same fixed top-right spot; exactly one is shown, based on whether `?data=` was present when the page loaded — real data and random fake data are never both an option at once. `updateRealDataBtn` starts with an inline `style="display:none"` (not a stylesheet rule) specifically so the reveal-it JS (`updateRealDataBtn.style.display = ''`) clears *that* inline override and falls through to the button's normal default display, rather than being masked by a stylesheet rule of its own.
- **"Update Real Data" re-fetches, it doesn't re-resolve**: `updateRealData()` re-fetches the already-remembered `realDataUrl` if one exists; it only redoes the QR-resolution step if `realDataUrl` is still `null` (i.e. the very first load failed) — so repeated presses are cheap and don't hit the QR endpoint every time.
- **No build-time secret handling needed, because there isn't a secret in the code**: the actual per-installation QR URL is supplied at runtime via the `?data=` param (by whoever links to this page for their own laundry room), never hardcoded here — this file and `src/app.js` only ever reference the general `mycscgo.com` API shape, not any specific location/room/QR code.
